## Required pipeline

1. Capture mutation/security audit events durably with the operation. When the operation already uses PostgreSQL, write the audit event/outbox entry inside the same short transaction. Do not enqueue a claimed-success event before that transaction commits.
2. Transfer Main's local staged events atomically into audit storage; the broker carries replaceable polling tasks. Sibling durable records need a bounded relay to Main. An after-commit callback is a wakeup optimization; polling must recover a lost wakeup. Keep the broker on persistent Redis, separate from the evictable response cache.
3. Dedicated audit consumers assemble bounded batches (initial target: at most 100 events or one second), persist with one PostgreSQL `INSERT ... ON CONFLICT (id) DO NOTHING`, and acknowledge only after commit. Preserve event IDs across retries. Keep the existing single-event task and internal endpoint as compatibility adapters.
4. Start with one audit writer process and a one-connection pool, zero overflow. Include each dedicated audit worker in the deployment connection budget. The default four-service topology reserves four audit connections in addition to API, general-worker and integration pools. Increase throughput by measuring batch efficiency before adding writers. Do not move sibling services onto Main's database credentials.
5. Retry transient failures with bounded backoff; retain failed durable records with visible recovery status. A broker outage must not fan out into synchronous database writes from every API request. Durable capture is required before removing that fallback.

## Volume policy

Always retain writes, authentication failures, account/role/session changes and sensitive administrative access. Continue skipping anonymous safe reads. Treat routine read analytics separately; sampling or aggregation must not silently discard security audit events. Keep payloads small, omit bodies unless needed for the event, redact credentials and avoid duplicating whole ORM graphs.

## Operations

Monitor oldest pending event age, pending count, batch size, persistence latency, retries, terminal failures, duplicate suppression and audit connection utilization. Alerts should trigger on growing lag and failed recovery, not only queue length. Retention runs in bounded batches outside peak traffic; audit-table partitioning/index changes require real query-plan evidence.

Legacy Celery audit persistence tasks have a 30-second soft limit, 45-second hard limit, and at most five transient-error retries with exponential backoff capped at 60 seconds; a valid receiver Retry-After can request a longer delay. Main's durable drain uses the same time limits and recovers failed transactions through subsequent polls. Prefetch and audit-worker concurrency are one in Compose. Load measurements beyond the sequential storage microbenchmark remain required.

Each Research, Library and HERI audit relay task uses a stable service/job advisory key.
